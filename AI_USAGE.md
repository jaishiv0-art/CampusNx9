# AI usage
## Models / APIs used at runtime (optional)
| Model | Where | Purpose |
|---|---|---|
| Anthropic Claude (model id from `LLM_MODEL`, default `claude-sonnet-4-6`) via the Messages API | `backend/app/llm.py` | Classify the intent of an assistant message and pull out hints (course name, day, target day, "tomorrow"). Nothing else. |

No API key => `llm.classify()` returns `None` and the deterministic rule-based path in `backend/app/assistant.py` + `backend/app/core/nlp.py` handles everything (tested: `test_assistant_works_without_api_key`). Booking extraction (English + Hinglish) is deterministic and does not call any LLM.

Prompt location: `SYSTEM` constant in `backend/app/llm.py` (the only prompt in the project).

## Hard restrictions on the LLM
The LLM **may**: understand text, extract fields, suggest a clarification question.
The LLM **must not and cannot**: decide validity, approve/reject, change a schedule, invent availability, bypass the engine.
Enforced in code, not by prompt: its output is whitelisted to six intents; it never receives timetable data; feasibility comes only from `core/week.py`, `core/checker.py` (official validator), `core/bookings.py`, `core/solver.py`; every proposal is stored as *pending* and re-validated by the deterministic checker at approval time; approval needs an authorised human who is not the requester. Explanations are assembled from real constraint checks and recorded decisions, never generated by the LLM.

## AI development tools
This codebase was written with Claude (Anthropic) as a pair-programming assistant in a chat session: architecture, solver model, booking engine, parser, API, UI and documentation drafts. A human must review it and run the verification in README.md; the assistant's sandbox had no network, so OR-Tools/FastAPI parts were not executed there (see README "Verification status").
